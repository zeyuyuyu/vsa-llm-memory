# NSR4 pre-registration: a state-estimation engine that repairs the reader's events

Date: 2026-11-11. Written after development on dev, the retired test and nsr1 (nsr2 is excluded from development and
from the held-out role: its errors were inspected for NSR2/NSR3); committed before the held-out split nsr3 exists.

## Question

NSR1-NSR3 showed that every miss is a misread state fact and that the downstream engines are exact. NSR2's engine could
flag risky answers but never changed one. NSR4 asks whether an engine that checks the reader's events against symbolic
consistency rules, repairs them, and rebuilds the state can make answers right more often without breaking right ones.

## Engine (nsr/nsr4.py at this commit)

The reader's events replayed in order reproduce the product's state exactly (88/88 development logs). The engine repairs
each message's events, then replays:
- **R1 duplicate swap:** a message read as the same swap twice is one swap (two identical swaps are a no-op, which nobody
  reports). Development: 33 occurrences, the truth had exactly one swap in all 33 (a reader/memory defect in the product,
  reported to the user; apps/real is not edited).
- **R2 double assignment:** one thing given two places by the same human message: the first stands; a later place goes to
  a named but unplaced item, else it is dropped.
- **R3 type violation:** a move the containment-type table (learned from truth histories of the training splits) forbids,
  e.g. a rack into a box, is dropped.
Arms: **E0** the reader's events as they are (the product); **E1 = R1 + R3** (primary; both repaired facts only, never
broke one, in development); **E2 = R1 + R2 + R3** (R2 broke 1 final fact and 58 fact-line states on the retired test).
The type table for the held-out run is learned from dev + retired test + nsr1.

## Data

Held-out **nsr3**: 40 fresh logs (10 per scenario, seeds 600+), generated after this commit with the vendored generator
and Qwen3-32B (rev 9216db57) on the A800 box, read by the shipped reader. Questions: NSR1's end-state impact questions
(230) and NSR3's temporal window questions (460), generated by the committed code.

## Measures and bars (nsr3)

- **S1:** E1 end-state impact accuracy - E0 >= +0.010.
- **S2:** E1 temporal-window accuracy - E0 >= +0.015.
- **S3 (precision):** final-state facts E1 breaks (right under E0, wrong under E1) <= 0.2 x facts it repairs, and at least
  3 facts repaired (else the run cannot measure precision).
- **S4 (history precision):** fact-line states E1 breaks <= 0.1 x those it repairs.
Reported: E2 on every measure; R1/R3 firing counts; final-fact accuracy; per-scenario numbers; every broken fact inspected.
Independent check: the gold answers come from nsr1_score / nsr3_score (own replay), which share no code with nsr4.py.

## Predictions

S1 holds (about +0.02), S2 holds (about +0.03), S3 and S4 hold (no broken facts expected). E2 adds little over E1 and may
break facts. What a pass would support: symbolic consistency checking of the reader's output repairs a measurable part of
its errors; the engine contributes accuracy, not only flags. What it would not: that the rules cover the reader's main
failure modes (most remaining misses are plausible wrong places no rule can see).
