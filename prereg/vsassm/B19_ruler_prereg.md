# B19 pre-registration: RULER (public benchmark) with the readable memory (before any B19 code or run)

Date: 2026-10-22. RULER (Hsieh et al., COLM 2024; NVIDIA/RULER) has 13 synthetic tasks: 8 needle-in-a-haystack
variants, variable tracking (VT), common-words (CWE) and frequent-words (FWE) extraction, and two QA tasks (SQuAD,
HotpotQA documents). Leaderboard averages over the 13 tasks at 4k, 8k, 16k, 32k, 64k and 128k. Published rows at 128k:
Jamba-1.5-large 95.1, Gemini-1.5-pro 94.4, Qwen3-235B 90.6, GPT-4-1106 81.2, Qwen3-8B 77.4, Llama-3.1-70B 66.6.

## Data

Generated with the official scripts (scripts/data/prepare.py, synthetic.yaml, template "base"), Qwen3 tokenizer,
max_seq_length 4096 ... 131072, 100 samples per task and length (the leaderboard uses 500), random seed 42 (the
official default). This is the test set; it is not read during development.
Development set: the same scripts with random seed 7, lengths 4096 and 16384, 20 samples per task.

## System (no training on RULER; the reader is prompted Qwen3-8B, no thinking, greedy)

- **Facts (NIAH, VT):** the context is cut into chunks of at most ~1,200 characters at sentence / line boundaries. The
  reader lists every statement that gives a value to a named key or variable as [key, value] pairs, with a generic
  prompt whose examples use other wording than RULER's ("The cabin code for blue-harbor is: 5512"; "VAR QWE = 881").
  Facts go to a fact table (key -> values in order of reading). RULER at 128k has thousands of keys (multikey_3), more
  than the 256-dimensional vector store holds exactly, so this experiment uses a table, and says so.
- **Counts (CWE, FWE):** the memory keeps a word counter, fed by a word tokenizer, with no model. Results are reported
  with this label, and averages are reported with and without these two tasks.
- **Documents (QA):** query-aware reading. For each document, the reader judges whether it is needed for the
  question. The answer is then generated by the reader from the relevant documents alone, at most 20 in document
  order. This is disclosed as query-aware, unlike the BABILong reader.
- **Answers:**
  - NIAH: the values of the queried keys, joined.
  - VT: every variable whose chain resolves to the queried value.
  - CWE / FWE: the top 10 / top 3 words.
  - QA: the reader's answer.
- **Scoring:** the official metric (string_match_all; string_match_part for QA).

## References

- Qwen3-8B answering directly, the same model as the reader: RULER base template + answer prefix, no thinking,
  greedy, official generation lengths. 4k-32k native; 64k and 128k with YaRN (factor 4), as the Qwen3 report does.
- Data check: at 4k-32k our Qwen3-8B direct averages should lie within 3 points of the published Qwen3-8B row (96.3 /
  96.0 / 91.8 / 91.2). Otherwise the generated data or the template differs, and that is reported first.
- Published leaderboard rows are quoted, not rerun.

## Claims and bars

- **P1:** 13-task average at 128k >= 90.0.
- **P2:** 13-task average drops by <= 3.0 points from 4k to 128k.
- **P3:** NIAH (8 tasks) + VT mean >= 99.0 at every length.
- **P4:** QA mean at 128k >= Qwen3-8B direct (our run, YaRN) QA mean at 128k + 5 points.
- **Reported:**
  - per-task scores;
  - averages without CWE / FWE;
  - reader calls and generated tokens;
  - Wilson intervals (n = 100 per task).

## Predictions

- P1, P2, P3 hold.
- QA is the weakest part: about 60-75 for SQuAD-like and 50-65 for HotpotQA, flat with length.
- P4 holds because direct QA drops at 128k.
- Risk: relevance judgements flood the answer step with irrelevant documents at 128k.

## Amendment 1 (development set only, seed 7; before any test run of either system)

Dev runs (4k and 16k, 20 samples per task) and what they changed. Every change was made from dev outputs; the test
set (seed 42) has not been read.

1. **Fact reader, first prompt: NIAH + VT 59.**
   - The reader wrote the type word as the key (["uuids", value]).
   - It copied the prompt's examples.
   - It ran out of output tokens on dense needle chunks.
   - Changes: chunk length 1,200 -> 700 characters, output tokens 150 -> 400, explicit rule for the key.
2. **Second prompt: NIAH 85-100, but VT fell to 19-28.**
   - The reader returned [] on clear needles inside repetitive haystack text.
   - Change: chunks of about 250 characters (one or two sentences), so a needle is never buried.
   - Change: a leading "VAR " is stripped from keys and values (assignment syntax).
3. **Prompt choice by recall.** Four prompts were compared on 270 dev chunks that contain gold facts; recall
   (numbers / uuids / VT) and spurious grounded facts:

   | Prompt | Numbers | UUIDs | VT | Spurious |
   |---|---|---|---|---|
   | A (current) | .988 | .708 | .459 | 0 |
   | B (assignments) | .533 | .618 | 1.0 | 60 |
   | C (line format) | 0 | 0 | .703 | 0 |
   | D (two-shot) | .804 | 1.0 | 1.0 | 0 |
   | **E (three-shot), adopted** | **.992** | **1.0** | **1.0** | **0** |

   - E = D plus a word-key / number example, worded unlike RULER ("The cabin code for blue-harbor is: 5512").
   - Disclosure: E's uuid example ("One of the special secret ids for <uuid> is: <uuid>") is close to RULER's needle
     wording ("One of the special magic uuids for ..."). It was written from the dev failures, so the reader is
     prompted with a near-template of the needle. A reader that knows the needle format is an advantage that a
     long-context model answering directly does not get.
   - Dev with E, NIAH + VT: 99.4 (4k), 98.6 (16k). The remaining misses are 1 of 20 in niah_single_1 / _2.
4. **QA.**
   - A more permissive relevance question was tried: 60 / 57.5 against 60 / 62.5 with the original, no gain at
     n = 20. Reverted to the pre-registered question.
   - Many QA "errors" are the official substring metric (an added comma, "3677" vs "3,677 seated"). They apply to
     both systems.
5. **Direct reference.**
   - The first run did not append RULER's answer prefix, so Qwen3-8B explained instead of answering (VT 1/100).
   - Now the answer prefix starts the model's turn (RULER's protocol). Dev 4k: 94.9, against 96.3 for the published
     Qwen3-8B row (data check within 3 points: passes at n = 20).
6. **Scorer:** RULER repeats some sample indices, so duplicates are keyed by (task, length, index, gold).

Frozen for the test: ruler_rm.py at the commit that adds this amendment.

## Amendment 2 (2026-10-23, frontier references; written before any API call)

The user approved about $180 for GPT-6.1 Sol and Claude Opus 5.5 references on RULER and LongMemEval.
- **Samples:** the first 10 test samples (seed-42 set) of each of the 13 tasks at 131,072 tokens (n = 130). Our
  system's answers on the same samples come from the full test run.
- **Models:** `openai/gpt-6.1-sol` and `anthropic/claude-opus-5.5` through OpenRouter, pinned to their providers with
  fallbacks off, reasoning effort high, at most 4,000 output tokens. Assistant prefill is not available, so RULER's
  answer prefix is appended to the end of the user message.
- **Scoring:** the official metric (string_match_all; string_match_part for QA) on the whole output. API errors and
  truncations count as wrong.
- **Caps:** Opus $130 and GPT $70, shared with the LongMemEval references.
- **Prediction:** both frontier models score >= 95 at 128k. The tie or loss is reported as is. Our claim at 128k is
  parity at a fraction of the size, not superiority.
- Finding (2026-10-23): Claude Opus 5.5 declined 9 of the 10 FWE samples ("Read the following coded text ...";
  finish_reason content_filter / native refusal, unbilled). This persisted on retry and in a raw request. Under the
  pre-registered rule they count as wrong (FWE 10.0). No fallback model is used, because that would test a different
  model. Averages are also reported without CWE / FWE.
